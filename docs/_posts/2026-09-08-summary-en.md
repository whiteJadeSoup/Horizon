### [512-bit RSA key of a 1990s Certificate Authority factored on a consumer GPU](https://mcpherrin.ca/2026/09/07/rsa.html) ⭐️ 7.0/10

A security researcher factored the 512-bit RSA private key of a Certificate Authority from the 1990s in roughly two days using a consumer GPU, then rebuilt the original certificate to demonstrate it still works. Because modern TLS libraries have dropped the legacy protocols required — Go&\#x27;s crypto/tls removed SSLv3 support in Go 1.14 — the author wrote a custom TLS implementation to serve the resurrected certificate to Netscape Communicator 4.51, covering both its 40-bit export build and its 128-bit US build, with the client&\#x27;s clock set to the year 2000 to satisfy certificate validity checks. The demonstration, which involved export-grade ciphers and earned four automatic &\#x27;F&\#x27; grades from an SSL testing report, underscores how trivially breakable 1990s-era cryptography has become on today&\#x27;s commodity hardware. The author acknowledged that some parts of the work relied on LLM-generated output that was not fully verified, and the underlying weakness of 512-bit RSA is a well-established result rather than a novel break.

hackernews · ahlCVA · Sep 8, 01:16 · [Discussion](https://news.ycombinator.com/item?id=49604637)

**「Background」** During the 1990s, United States export controls capped the cryptographic strength of software shipped internationally, which is why browsers like Netscape Communicator 4.51 shipped with 512-bit RSA certificate authority roots — including two from the now-defunct Canadian CA E-Certify in March 1999 — and 40-bit export-grade ciphers. RSA security rests on the difficulty of factoring a key&\#x27;s large modulus, and 512-bit keys were already considered too weak when the 512-bit number RSA-155 was factored in 1999; today, the open-source tool CADO-NFS can break such keys on a single desktop in roughly 30 hours. Because modern TLS libraries have dropped the SSLv3 protocol these legacy clients require, the author had to write a custom TLS server in Go to serve the resurrected certificate to Netscape 4.51.

**「Impact」** Any certificate, system, or archived traffic still relying on 512-bit RSA — the export-grade key size of 1990s TLS — must now be treated as effectively unprotected, since a consumer GPU can factor such a key in roughly two days. Because much traffic of that era used non-ephemeral RSA key exchange rather than ephemeral keys, recorded ciphertext from the period can also be retroactively decrypted, reinforcing harvest-now-decrypt-later concerns.

**「Readers on LLM reliance and harvest-now-decrypt-later」** Commenters criticized that key parts of the write-up leaned on unverified LLM output, with one arguing that only outputs actually tested should be trusted since plausible-looking generation is exactly what LLMs do, while others enjoyed details like the SSL report&\#x27;s four automatic &\#x27;F&\#x27; grades. A recurring concern was harvest-now-decrypt-later: since much 1990s traffic used static keys or no encryption at all, one commenter wondered which governments might be recording today&\#x27;s encrypted traffic in anticipation of future decryption capabilities.

### [Study examines how well AI coding agents apply testing and formal verification](https://danluu.com/agentic-testing/) ⭐️ 7.0/10

Dan Luu published an empirical study on danluu.com investigating how well AI coding agents apply testing and formal verification techniques when producing code. The post drew substantive discussion on Hacker News \(57 points, 11 comments at the time of collection\), where readers debated the experimental methodology and the agents&\#x27; apparent limitations with formal methods. Formal verification tools raised in connection with the results include TLA+, Verus, Creusot, and Lean, alongside conventional software testing practices. The topic matters to developers and teams adopting AI-assisted software engineering because it addresses whether agent-written code can depend on the agents themselves to be adequately tested or verified. The supplied material does not reproduce the article&\#x27;s detailed findings, so readers should consult the original post for specific results.

hackernews · vinhnx · Sep 8, 02:58 · [Discussion](https://news.ycombinator.com/item?id=49605246)

**「Background」** AI coding agents are LLM-based tools that autonomously write and modify code, while formal verification techniques—such as TLA+ specifications and proof assistants like Verus, Creusot, and Lean—allow engineers to mathematically prove properties of programs rather than relying solely on example-based tests. The study is framed around a deliberately practical question: whether simple instructions telling an agent to use particular testing techniques or libraries improve implementation correctness, simulating a developer with no testing expertise who has merely heard that such techniques are recommended. This framing matters because it measures how agents perform under typical, non-expert guidance rather than under the direction of verification specialists.

**「Impact」** Developers who rely on AI coding agents gain a dedicated empirical reference point suggesting these tools apply testing and formal verification techniques unevenly, which argues for building stronger automated test and review loops around agents rather than assuming they will self-verify their output. Because commenters dispute whether the experiment validly separates testing practice from code architecture, the findings are best treated as directional evidence rather than a definitive benchmark of agent capability.

**「Community discussion」** Reactions were mixed: one commenter argued the experiment &\#x27;makes little to no sense&\#x27; because effective testing cannot be decoupled from code architecture, which the author reportedly does not describe, while another found weak formal-verification results unsurprising given how little TLA+, Verus, Creusot, and Lean code exists for models to learn from, proposing instead a test of whether agents can implement a manually written high-level spec. Other observations included that agents know techniques like making illegal states unrepresentable but skip them unless idiomatic to the language, that harness tuning may matter as much as the models themselves, and one reader expressed surprise at the results, having expected agents to test code reasonably well.

### [Broadcom Pulls VDDK Downloads, Raising the Cost of Leaving VMware](https://www.virtualizationhowto.com/2026/09/leaving-vmware-just-got-harder-after-broadcom-pulled-vddk-downloads/) ⭐️ 7.0/10

Broadcom has removed public downloads of the VMware Virtual Disk Development Kit \(VDDK\), the SDK that third-party tools rely on to read and convert VMware virtual disks. Migration and conversion utilities used to move workloads off ESXi commonly depend on the VDDK, so pulling it raises the practical cost and complexity of leaving VMware. The change lands as Broadcom continues reshaping VMware&\#x27;s licensing and product strategy, which has already pushed many enterprises and homelab users to evaluate alternatives such as Microsoft Hyper-V and Proxmox. According to the article, VMware-to-Proxmox migrations are not affected by the removal. Critics see the move as another step toward tighter vendor lock-in around the Broadcom-owned platform.

hackernews · josephcsible · Sep 7, 20:32 · [Discussion](https://news.ycombinator.com/item?id=49602699)

**「Background」** The Virtual Disk Development Kit \(VDDK\) is VMware&\#x27;s official software library that lets third-party tools read and manipulate VMware virtual disks, and it has long been the primary mechanism that nearly all migration products rely on to move virtual machines off vSphere without installing agents inside each guest. Broadcom acquired VMware in late 2023 and has since restructured the business around subscription licensing and bundled offerings, prompting many enterprises and homelab users to evaluate alternatives such as Hyper-V, Proxmox, and KVM-based platforms. Against that backdrop, Broadcom&\#x27;s quiet removal of public VDDK downloads — with the portal returning errors and no deprecation notice or migration path announced — directly affects VMware-to-KVM and other exit routes that depended on the kit being freely available.

**「Slower and constrained VMware exit paths」** Third-party migration tool vendors and enterprises leaving VMware now face materially slower disk transfers, since VDDK was the fast read path and its no-redistribution license blocks workarounds, while vSAN-backed VMs cannot be migrated at all without it. The effect is uneven by destination, however: Proxmox VE 8.2&\#x27;s built-in ESXi import wizard provides an unaffected route for some migrations.

**「Community reaction」** Commenters largely read the removal as part of what a former VMware engineer describes as Broadcom extracting value from a platform it sees as past its innovative peak. Practitioners report mixed migration experiences — one who led a VMware-to-Hyper-V project this year finds Hyper-V&\#x27;s tooling disjointed by comparison, while another found moving VMs from ESXi to Proxmox surprisingly painless — and some worry VMware&\#x27;s ecosystem advantages could eventually be lost altogether.
